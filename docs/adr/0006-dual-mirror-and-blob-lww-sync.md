# 双端镜像 + 整体-blob LWW 同步

配置(pages + icons + layout_settings〔布局设置〕;主题为永久深色、不持久化、不纳入同步)在浏览器 IndexedDB 与服务端 MySQL 各存一份完整副本,互为备份:任一端丢失均可从另一端恢复。服务端保持权威——在线写入先到服务端、成功后回写本地镜像;服务端不可达时本地镜像以 `dirty` 标记临时接管,重连后经「和解」推送。和解采用**整体-blob 末写获胜(LWW)**:比较本地"上次服务端确认时间"与服务端 `config_version.updated_at`(每用户一行,任何配置写都在同一事务里 bump),新者整份赢。

之所以选整体-blob 而非逐实体 LWW:单用户个人新标签页、数据量小、并发仅来自"我自己开了两个浏览器",逐行 `updated_at` + 墓碑表的复杂度换不回相应的正确性收益;blob 模型还让删除免费(新 blob 不含某图标即删)、且天然贴合已有的 `GET /api/config` 整体聚合。代价是两端真分叉时旧的那一整份丢失——该场景罕见且可立刻察觉,并以下规则兜底:冲突时服务端赢,但本地分叉存入 `conflictBackup` 并提示导出,绝不静默丢数据。

## 备选方案(已否决)

- **逐实体 LWW + 墓碑表**:更精细,分叉时只丢冲突行;但需给 pages/icons/settings 加 `updated_at` 列、维护墓碑表、写按 id 合并算法,复杂度显著高于单用户场景所需。
- **`persistQueryClient` 持久化 React Query 缓存**:代码更少,但缓存是不透明 blob,`dirty`/时间戳/和解/冲突备份无处挂载,会把最关键的同步逻辑塞进框架缝隙,难维护。
- **跨设备实时推送(SSE/WebSocket)**:需求仅为"离线可用 + 灾难恢复",非多端协作;推送通道 + 在线检测 + 并发合并的复杂度不划算,跨设备改用"加载时拉取最新"即可。
