# 趋势描述译制口径修订:撤汉字启发式,全量送译

背景:ADR-0030 第 3 条以逐条汉字启发式做语言判定——描述含汉字即视为中文跳过送译,否决 LLM 自判(理由:「中文原样回显」与「该条失败」混进同一编号协议,区分成本大于几行正则)。2026-08-27 用户报障「周/月榜描述存在未翻译内容」。线上实证(diagnostic 脚本复刻生产解析 + 直查 `trending_translations`):**无汉字描述的译文覆盖率 100%,译制链路零故障**;未翻译条目全部是**含汉字被整条跳过**的中英混排描述——周榜 `awesome-gpt-image-2`(英文开头+汉字主体)、月榜 `reverse-skill`(343 字符几乎全英文,尾部夹汉字)。周/月榜比今日榜更易混入中国开发者的 README 项目(生命周期长),其英文开头的描述在 UI 上观感即「未翻译」。

**决策:趋势描述全量送译,删除 `HAS_HAN` 域过滤;「已是简体中文 → 原样输出,英中混杂 → 整体译成连贯中文」交由 prompt 约束(约束第 5 条)裁决。**

1. **重开 0030 裁决的依据是危害不对称**:启发式误伤是确定性的——每个混排条目必然不译,而这恰是用户报障的形态;LLM 裁决的错误形态温和(措辞偏差、偶发漏号走既有 null 不入库下轮重试),悬停原文兜底依旧成立。0030 预设的最坏形态「含汉字日文保留原样」在实际榜单上并非最坏——英中混排才高频。
2. **成本顾虑随终身缓存摊平**:新增送译量 = 榜单本就存在的纯中文条目(实测 1–3 条/榜),哈希即身份同原文终身只译一次,批内开销可忽略;20 条/批上限内未观察到结构性压力。
3. **连带修复 0030 自认盲区**:含汉字的日文描述此前保留原样,现由 LLM 正确译成中文,行为严格更优。
4. **判定语义从代码常量移入 prompt 文本**:可读性略降,以 `trending.ts` 头注与方法注释锚定本 ADR 补偿;`ensure` 的 filter 形参保持显式传 `() => true`(地基要求调用方明示域口径)。

**代价与取舍。** 换来混排/日文等所有非纯英文形态的正确中文化;付出:纯中文条目占用批次行的少量 token(终身缓存摊平)、语言判定不再可静态断言(回归测试改以 fake translator 收到的送译集为观察点,trending.test.ts 锚住全量送译口径)。
