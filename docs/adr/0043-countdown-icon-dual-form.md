# 倒计时图标化双形态:图标承载唯一编辑入口,时钟弹层降只读

背景:「倒计时」原是时钟 hover 弹层的附属分区(CONTEXT.md 旧口径):30 天窗内两路数据源(内置「节假日」+「重要日子」)混排,尾部挂「编辑」入口开 CountdownEditModal。诉求是图标化——1×1 常显下一条临近条目、点开可编辑「重要日子」。形态分叉有三个候选:①撤弹层,编辑与展示全迁图标;②弹层原样保留(两处展示 + 两处编辑);③弹层降只读(两处展示、编辑单点进图标)。附带口径问题:块内「下一条」限不限 30 天窗。

**决策:候选③;块内不限窗,两口径分层进 lib/countdown;数据归属维持 ADR-0026 不重开。**

1. **弹层降只读**:hover 时钟看「接下来有什么」是自然动线,弹层的 glance 价值保留;但两处编辑入口 = 同一 CRUD UI 两套维护,且新增图标的抽屉动线已把「配置」心智聚到图标侧。编辑入口全局唯一在「倒计时」图标详情 Modal(单 tab:「重要日子」可编辑 +「节假日」只读,CountdownEditModal 内容平移进 CountdownModal 后退役)。空窗时弹层分区**整体隐藏**——旧「保留一行编辑入口否则第一条无处可加」的理由随入口迁走而消失。
2. **块内不限窗**:弹层 30 天窗是**列表语境**的取舍(窗口外条目撑长列表无益);1×1 常显 glance 视图的意义是看着下一条逼近,哪怕还有 300 天。节假日 21 项/年足够密集,「下一条」恒存在。落为两口径:`getAllCountdowns`(全量升序,块内取 [0]、Modal 节假日分区过滤 source)与 `getCountdowns`(≤30 天,弹层,行为不变),后者是前者的过滤器;「今天/明天/N 天」措辞提为 `describeDays` 纯函数三处共用。
3. **数据归属不动**:「重要日子」仍寄放 `layout_settings.important_dates`(ADR-0026),图标是纯视图——写路径复用整份 PUT、同步/镜像/备份/和解链路零改动,后端唯一改动是 ICON_TYPES/SINGLETON_TYPES 两行枚举(countdown 1×1 无需 TYPE_SPANS)。
4. **登记形态**:扩展类型、单例、无实例参数(editor 空,AddDrawer 一键添加)、`detailEntry:'block'`(1×1 无滚动主体,整块点击开详情,自选股先例);块内主行 = 剩余天数、次行 = 条目名(扫一眼的核心量是「还有多久」,名称靠次行 + 名称行「倒计时」定位)。

**代价与取舍。** 换来:编辑单点(图标 Modal)、弹层保信息价值且更薄(纯展示分区)、常显 glance 不受列表窗口约束。付出:同一数据两处呈现,弹层与块内口径**不同**(弹层 30 天窗、块内不限窗)——这是刻意的(语境不同),但对未来维护者是认知负担,本 ADR 即记录;时钟弹层若日后彻底失去使用价值,撤除只影响 Clock.tsx 一处分区,图标侧自足。
