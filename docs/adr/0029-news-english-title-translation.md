# 新闻英文源标题译制:标题哈希译文表,复用更新日志译制链

背景:「新闻」15 源中 Hacker News、Product Hunt 两源标题为英文,中文用户阅读有门槛。后端已有完整的 LLM 译制基础设施(「更新日志」,ADR-0005/0017):AIHUBMIX 网关 + 候选模型链(候选失效换路)+ SHA-256 原文哈希主键的持久化译文表,「一版终身只译一次、失败保持英文、无 Key 拒绝」。

**决策:照搬更新日志译制范式到新闻标题——SHA-256(标题) 主键的独立译文表,补译内联进轮询链路;译制只认源清单,不做语言检测。**

1. **译文表独立于条目池、永不裁剪**:条目池每源滚动 50 条,但热帖会裁后再回炉、同一故事跨源同题——译文按标题原文哈希共享,回炉即命中、零成本复用;表年增几万行(每天百余新标题),SQLite 量级无害。**否决 `news_items` 加 `title_zh` 列**:窗口裁剪连译文一起删,同标题回炉重付钱,且跨源同题无法共享。
2. **补译内联进 `pollSource`,否决独立 cron 扫描**:入库后同轮扫该源缺译文行,新条目当轮出译文;存量补译零额外机制——功能上线后首轮 `pollAll` 扫到的全是缺译文行,天然全量补译(约百余条,一次性)。失败条目哈希未写,下一轮(30min)自然重试,免费的重试回路,对齐 changelog「失败不入库待下轮」口径。
3. **批量编号列表(≤20 条/请求),批间串行**:标题短,逐条请求在存量补译首轮是百余个请求,慢一个数量级且对 free 渠道限流不友好(changelog 纪律「不并发」);编号进出按行配对,漏行/畸行视为该条失败下轮重试。候选模型链与 `isCandidateExhausted` 换路判定照搬 changelog。
4. **env 复用不拆分**:`CHANGELOG_LLM_MODEL` + `AIHUBMIX_API_KEY` 一个键管全部 LLM 译制,少一个配置面;译制质量需求(标题短译)无按模块分化迹象,真要分化再拆不迟。
5. **只译认定的英文源,否决逐条语言检测**:按源硬编码 `{hackernews, producthunt}`(同「新闻源」代码即配置风格);检测要引语言库,且中文源偶发英文标题(译不译)两难,清单明确可预期。
6. **降级与展示口径全对齐 changelog**:无 Key 拒绝、失败 warn 保持英文——宁英勿空;wire 契约 `NewsItem` 加 `titleZh: string | null`,前端显示 `titleZh ?? title`,HTML `title` 悬停属性反转放英文原文供核对;译文后补靠既有节奏自然到达(staleTime 5min + 窗口聚焦重拉 + Modal 打开 refetch),不新增前端轮询。
7. **prompt 口径**:HN 惯用前缀(`Show HN:`/`Ask HN:`/`Tell HN:`)与方括号标注(`[video]`/`[pdf]`)保留原样只译正文;专有名词、产品名、代码标识符、emoji、定价词原样;不扩写不解释,长度贴近原文。
8. **不透出「译制阶段」**:新闻译制是后台批处理(一轮几十秒内完成),无 changelog 按需补译的排队可感等待,status 端点与前端排队态不值得为其存在。

**代价与取舍。** 换来标题译文终身复用、全用户共享(条目池本就全局共享,译文随池共享自然)、上线即自动补齐存量;付出一张永不清理的译文表(清理即重付钱,量级无害)、新条目入库到译文可见隔一轮 feed 刷新(聚焦窗口/重开 Modal 即见)、批量请求的漏行条目要等 30min 下轮(标题短失败率低,可接受)。
