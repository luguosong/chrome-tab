# 趋势仓库描述中文译制:trending_translations——「不落库」原则的精确例外

背景:「GitHub 趋势」(ADR-0028)内存缓存 TTL 1h、明确不落库;但用户以 repo 描述为了解项目的第一途径,英文(及日/韩/俄等)描述需译成中文展示。后端已有两代 LLM 译制基础设施(changelog ADR-0005/0017、news ADR-0029):候选模型链 + 原文哈希译文表,「终身只译一次、失败保持原文、无 Key 拒绝」。

**决策:新增同构译文表 trending_translations,补译内联进抓取链;语言判定用汉字启发式,不引语言库。**

1. **落库例外是本 ADR 的核心争议**:0028 的「不落库」指**易失的榜单排名**——组合缓存、TTL、内存,皆因榜单数据廉价可重抓。译文不同:「原文→中文」是永久事实,生命周期与榜单无关;热项目连日/连周在榜,纯内存译文每小时随缓存过期重译重付钱,违背译制体系「终身只译一次」的立足点。哈希即身份自然处理描述变更:改描述 = 新键自动重译,改回旧值免费命中;孤儿行(描述改版后的旧译文)不清理,同 news 口径,年增几百行量级无害。
2. **照搬 news 补译范式(ADR-0029 第 2/6 条)**:内联进 get() 抓取成功路径、fire-and-forget——首批响应先回原文,译文落表后靠前端既有节奏(staleTime 5min + 窗口聚焦重拉 + Modal refetch)与缓存命中路径的读侧 join 自然到达。非默认组合首开英文、二次到达,接受(与新闻「新条目隔一轮见译文」同款)。失败哈希不写,下轮组合过期重抓或 cron 1h 保热自然重试,零额外重试机制。
3. **汉字启发式,否决语言库与 LLM 自判**:trending 无「源」维度,新闻按源硬编码英文源的前提在此不成立,必须逐条判定。含汉字 → 视为中文不译(一行正则,零依赖零 token);无汉字的假名/韩文/西里尔照送译成中文,正合「非中文都译」。误判形态温和:含汉字的日文描述保留原样而非错译。LLM 自判则要把「中文原样返回」与「该条失败」混进同一编号协议,区分成本大于省下的几行正则。
4. **批量机制跨域提升**:news/translate.ts 的候选链 + 编号协议 + 限流纪律提升为 src/translate.ts(makeBatchTranslator),news 与 trending 各持域特化 system prompt——第三实例(trending 描述)出现,机制从 news 域归位为跨域件;news 行为零变化(测试回归佐证)。env 沿用 CHANGELOG_LLM_MODEL + AIHUBMIX_API_KEY 一键管全部 LLM 译制(ADR-0029 第 4 条)。
5. **wire 与展示**:TrendingRepo 加 descriptionZh: string | null(null = 未译/失败/无 Key/原文即中文/无描述),前端 descriptionZh ?? description,悬停 title 放原文核对(新闻同款);tile 行悬停 title 同享译文。描述本身完整换行展示、永不省略(2026-08-26 产品决策)。

**代价与取舍。** 换来热项目描述终身只译一次、全用户共享、描述变更自动跟踪;付出:0028「不落库」原则开一个精确例外(落的是译文不是榜单,边界以本 ADR 记录)、一张年增千行级新表、非默认组合首开英文的到达延迟、含汉字日文描述不译的启发式盲区(悬停原文兜底)。
