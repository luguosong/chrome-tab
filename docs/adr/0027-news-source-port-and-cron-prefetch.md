# 新闻图标:newsnow 源定义移植 + cron 预取落库,弃惰性刷新

背景:「新闻」(CONTEXT.md,单例 3×2 大 tile)要聚合 16 个内置「新闻源」(热榜/资讯页),每源保留最近 50 条窗口、跨会话稳定鲜度、勾选了才取数。参照开源 newsnow(MIT)——但它的源体系与缓存调度是一体的:`SourceGetter` 纯函数 + 请求时惰性刷新(interval/TTL 判定)+ SQLite 缓存表,无 cron。

**决策:只移植 newsnow 的源定义(每源一个抓取纯函数,MIT 允许照搬),调度与存储不跟——沿用本项目「视频更新」范式(ADR-0023):后端 30min cron 预取 + 落库,前端只读。**

1. **源定义可移植是参照的核心**:newsnow 的 `SourceGetter = () => Promise<NewsItem[]>` 与框架零耦合(统一 UA/超时/重试的 myFetch 之外无依赖),逐源搬转换函数,不引 newsnow 任何运行时依赖。展示元数据(id→中文名)进 shared 契约,照「外源」代码即配置模式。
2. **否决惰性刷新(newsnow 字面)**:它为多用户共享部署设计(缓存命中即省);本产品是新标签页,开页零等待最敏感——17 源过期时开页等最慢上游(实测 GitHub Trending 2.4s)不可接受。cron 预取让开页永远读库。newnow 用「批量读缓存灌屏 + 逐源刷新」缓解,本质是给惰性刷新打补丁,不如预取干脆。
3. **否决前端直连**:多数源无 CORS(热榜 JSON/HTML 抓取全挂);且每开一页对 16 个上游各打一次请求,放大上游压力也放大风控面。后端集中预取把上游请求压到每 30min 一轮。
4. **否决引 newsnow 整服务**:`docker pull` 一个 newsnow 实例再代理它,多一个部署单元、多一层网络跳、丢账号级勾选语义(它无此概念),为零收益多运维一件东西。

**代价与取舍。** 换来开页零等待、50 条窗口、勾选感知的按需轮询(勾了才轮询该源、勾选即时投递首取)、48 轮(30min/轮=1 天)失败标「取数失败」的自愈降级;付出源维护面(上游改版即坏,坏到源标记不炸图标)与 newsnow 上游漂移(移植即快照,不再跟随上游演进)。热榜类源无逐条发布时间(上游本就无此字段):行内时间自然省缺、红点不生效,混合流排序以入库时间为代理;标头鲜度位用源级最近成功抓取时间。weibo 源携带 newsnow 硬编码的游客 Cookie(会过期,过期即该源 failing,cookie 属可再抄的短期凭据);cls 复刻其动态签名算法。
