# 模型追踪:厂家专属确定性解析 + 全局持久档案,不开放任意信源配置

背景:「模型追踪」(issues/01 起片)汇集各「跟踪厂家」的 AI 模型与「模型动态」。研究(research/sources.md)结论:发布事实只有厂家一手信源可证——六家的发布页/目录/仓库**结构各异**(智谱是日期化 `<Update>` 块、OpenAI 是 changelog 日期段、DeepSeek 是无 RSS 的 HTML),且各家的坑互不相同(智谱目录混托管第三方模型、上游偶有张冠李戴的链接;xAI 的 `-latest` 是移动别名)。通用「RSS 聚合 + 关键词匹配」式方案在这片地上只会产出误报:把网关上架当发布、把别名迁移当新模型、把托管模型记成自研。

**决策一(解析):每家一段专属确定性解析器,基线人工核验。** 档案行(模型的基本资料:种类/阶段/开放方式/信源)只来自**代码内人工核验基线**——部署即幂等 upsert,代码即配置;自动解析只从该厂家主发布页提取**结构化**字段(智谱:`<Update label description>` 块 → 日期 + 描述 + 模型文档链接),且必须**双条件归属**(描述含基线 alias 且链接 slug 匹配,防上游链接张冠李戴——实测 GLM-Image 块误链 glm-4.7 文档页)。解析器不认识的更新块(基线外型号、第三方托管模型)只作待核验线索跳过,待人工核验后随基线纳入。语义化事件类型(api_available/weights_available 等)同样只在人工核验基线里,自动解析一律产 `updated`——不猜。

**决策二(档案):全局共享 + 持久化。** 三张表(`model_archive`/`model_events`/`model_fetch_status`)无 user_id——「模型档案」是全用户共享的事实(CONTEXT.md 词汇),用户只决定是否放置图标,不各自复制档案。后端 6h 轮询(研究 §6 节奏),单信源失败**保留最后成功结果并标记陈旧**(status 表 stale 位),基线数据保证首启即有内容;前端只读库(同 ADR-0023 范式,但无账号维度)。

**不开放任意厂家/信源配置(拒绝项):** 上游结构无稳定性承诺,解析器与信源是**代码级耦合**——让用户自配信源等于把「确定性解析」退化回「关键词猜测」,误报直接进事实链。新厂家只在其准确跟踪方式经确认后纳入(「跟踪厂家」的定义性约束),对用户呈现为固定 tab。同理拒绝:第三方聚合站作权威源(不可回链厂家一手事实)、AIHubMix 网关 diff 作发布事件(路由语义 ≠ 上游版本)、按标题去重(标题会回改——去重键 = 模型+类型+日期+信源,研究 §6.6)。
