# 更新日志副本持久化与定时预取:逐版本块哈希增量译制

取代 ADR-0005 的缓存与拉取策略(译制管线本身——GitHub 拉取 → LLM 译制 → 失败透传英文——不变)。

**推翻 0005 的三个前提。** 0005 断言「changelog 变更频率以周计,重启重译一次可忽略」,并以「最近 N 版切片」整体哈希作缓存键、纯内存单条存储。实际运行三点失血:(a) 本项目部署频繁,每次重启冷 miss,全量重译 5 版;(b) claude-code 高频发版(一天多版常见),切片哈希随任何新版变化,又全量重译 5 版——实际新增只有 1 版;(c) 懒加载模式下每次打开抽屉都同步打 GitHub ~1s。

**决策:把「一份副本」落库,增量按块计算。**

1. **译文表 `changelog_translations`**:主键 = 单个版本块原文的 SHA-256,一版一行、**永久保留**——每版终身只译一次。定时预取(最近 N 版)与前端按需补译(旧版)共用此表;落出窗口的旧版译文继续生效,文档顶部中文区随时间单调变长(0005 时代旧版恒英文)。
2. **快照表 `changelog_snapshot`**(单行):原文全文 + npm 发布日期 + 拉取时间。**原文是唯一事实源**,译文按块哈希覆盖其上拼装(overlay),不存拼装结果——快照与译文永不失配。
3. **6 小时定时预取**(`ChangelogScheduler`):启动先 `loadFromDb` 恢复内存镜像(零外呼、零 LLM、秒级可服务),再异步预热追平;此后每 6h 刷新。**请求路径纯读内存快照,零外呼零 LLM**——打开抽屉不再是拉取触发点。拉取失败沿用旧快照(数据最多旧 6h,永不空窗);DB 全空(首次部署)时首个请求同步兜底拉一次。
4. **更新检测纯算法**:原文逐版本块切分、逐块哈希比对,缺失才调 LLM(每块一次)。**零 token 花在「判断是否有更新」上**——LLM 只做翻译,不做判断。
5. **前端按需补译**:`POST /api/changelog/translate { versions: [...] }`,未译版本在 Drawer 逐版显示「翻译」按钮;译毕入库持久化,失效重拉即得新全文。GET 响应增加 `translatedVersions` 供前端判断哪些版本未译。

**取舍与否决。** 存储选 **MySQL 而非磁盘文件**:Flyway/连接池现成,数据随 MySQL 卷天然活过容器重建,文件还需新挂卷。译文**永久保留而非随窗口丢弃**:成本严格 ≤ 现状(每版恰好译一次),无清理逻辑,表每发版 +1 行(年增 ~百行,可忽略)。**否决自动全量回填** 361 版:一次性 ~164K token 花在几乎无人细看的旧版上;改为手动逐版补译,花钱的决策权留给用户。**npm 发布日期的独立 1h 内存 TTL 缓存删除**,并入 6h 刷新周期随快照持久化(外呼上限 4 次/天)。

**降级语义不变但节奏变了。** 译制失败(Key 失效/网关宕机)→ 该版保持英文、行不入库,**下一轮 6h 定时刷新自动重试**(0005 时代是每次请求重试——那正是要消灭的重复计费);拉取失败 → 异常止于调度方,内存快照照常服务。

**已知语义变化**:重启后若上游已发新版,首屏最多旧 6h(定时周期内的新版要等下轮预取或用户手动刷新);换来的是重启零 LLM 调用。发版灵敏度换成本,接受。
